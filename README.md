# AI-аудит отдела продаж в amoCRM

Архитектура AI-анализа продаж и Python-скрипт поиска сделок без открытых задач или с просрочкой.

В репозитории две части:

- **Архитектурное предложение:** как собрать данные CRM и звонки, рассчитать показатели и подготовить проверяемый отчёт для руководителя
- **Работающий пример на Python:** 50 строк, которые читают сделки и задачи через amoCRM API v4 и выводят JSON со сделками, требующими внимания

Сбор звонков, ASR, LLM, база данных и оркестратор ниже описаны как проект решения. Они не реализованы в этом репозитории. Скрипт не использует AI и не изменяет данные CRM.

## Предлагаемая архитектура

Поток данных:

```text
Запрос → Оркестратор → Сбор данных CRM и телефонии
                    → Расшифровка и анализ звонков
                    → Расчёт показателей → Отчёт с источниками
```

Оркестратор фиксирует момент T, период `[T − 30 дней; T)`, часовой пояс аккаунта и нужные воронки. Запускает четыре ограниченных по роли исполнителя. API, очереди и расчёты выполняет обычный код; LLM используется для содержания разговоров и текста отчёта.

1. **Сборщик CRM.** Читает `/leads`, `/tasks`, `/events` и справочники пользователей и воронок. Получает сделки, задачи, ответственных, сроки и историю смены этапов. Учитывает также старые сделки, с которыми работали в выбранном периоде. Первый запуск загружает доступные данные постранично, последующие сохраняют изменения. Дубликаты удаляются по ID и версии записи.
2. **Сборщик звонков.** Через API провайдера телефонии получает `call_id`, время, направление, сотрудника, длительность, результат и ссылку на запись. Конкретные методы зависят от провайдера. Связь со сделкой берётся из интеграции; иначе используются контакт, телефон и время. Неоднозначные совпадения требуют проверки человеком.
3. **Аналитик разговоров.** Через очередь получает доступные записи и расшифровки с разделением участников и таймкодами. Перед передачей согласованному поставщику LLM маскирует персональные данные. Извлекает потребность, возражения, договорённости и следующий шаг в JSON по схеме. Для вывода нужны `call_id`, подтверждающая цитата и таймкод; плохая запись отмечается как недостаток данных.
4. **Аналитик отчёта.** SQL/Python считает новые и закрытые сделки, переходы этапов, звонки и незавершённые задачи. Для конверсии задаётся когорта сделок, созданных за период; отдельно показываются выигранные, проигранные и открытые на T. LLM объясняет готовые цифры, группирует проблемы и предлагает действия со ссылками на сделки и фрагменты звонков.

**Хранение и надёжность.** PostgreSQL хранит сущности CRM, связи, метрики, результаты анализа и версии отчётов. Зашифрованное объектное хранилище хранит аудио и расшифровки с ограниченным сроком жизни. Очередь обеспечивает повторы, лимиты параллельности и бюджета; сбой одного звонка не теряет весь запуск. Токены хранятся отдельно от LLM, доступ выдаётся по ролям.

**Результат:** краткая сводка, проблемные сделки, примеры разговоров и предлагаемые действия. Отчёт показывает долю полученных данных и обработанных записей. Исторические показатели за 30 дней рассчитываются по событиям или снимкам; текущая просрочка показывается отдельно. Если истории не хватает, показатель не восстанавливается предположениями.

## Автоматизация и участие человека

Система собирает и сверяет данные, расшифровывает звонки, рассчитывает показатели, отмечает пропуски и готовит отчёт. Числовые показатели рассчитывает код.

Руководитель утверждает критерии качества и определения метрик, разбирает спорные связи звонков со сделками и проверяет выводы с низкой уверенностью. Изменение этапов, создание задач, сообщения клиентам и кадровые решения остаются за человеком. Для последующей автоматической записи в CRM нужны отдельные правила и журнал действий.

## Три главных риска

1. **Неполные данные и неверная привязка.** Запись может отсутствовать, задача может быть связана с контактом, у одного телефона может быть несколько сделок. Нужны проверка полноты выгрузки, доля несвязанных записей и отказ от автоматического объединения неоднозначных случаев. Сегодняшнее состояние задач не позволяет восстановить прошлую дисциплину без истории.
2. **Ошибки ASR и LLM.** Шум, несколько участников и неполный контекст искажают смысл. Нужны валидация JSON, подтверждающий фрагмент, проверка таймкодов и оценка на вручную размеченной выборке. Неподтверждённые выводы передаются человеку. Текст разговора считается данными и не может давать агенту команды или разрешать вызовы инструментов.
3. **Конфиденциальность и доступы.** До запуска согласуются основания обработки, поставщики ASR/LLM, место и срок хранения. Используются минимальные права, маскирование, шифрование и аудит доступа. Секреты не передаются модели; записи и персональные данные не попадают в логи без необходимости.

## Что делает скрипт

[`amocrm_overdue.py`](amocrm_overdue.py) получает текущие открытые сделки и незавершённые задачи, непосредственно привязанные к сделкам. Из выборки исключаются удалённые сделки и сделки в финальных статусах `142` и `143`.

Сделка попадает в отчёт, если:

- у неё нет ни одной незавершённой задачи: `reason = "no_open_tasks"`
- у неё есть хотя бы одна незавершённая задача с `complete_till < now`: `reason = "overdue"`

Завершённая задача не считается запланированным следующим шагом. Просрочка сохраняется, даже если у сделки одновременно есть другая задача с будущим сроком. Задача со сроком ровно `now` не считается просроченной.

Вывод содержит `lead_id`, `name`, `responsible_user_id`, `reason` и `overdue_task_ids`. Пример с вымышленными данными:

```json
[
  {
    "lead_id": 123,
    "name": "Пример сделки",
    "responsible_user_id": 10,
    "reason": "overdue",
    "overdue_task_ids": [456]
  }
]
```

Скрипт выполняет только GET-запросы, использует постраничную загрузку по 250 записей, таймауты соединения/чтения и повторные попытки для `429`, `500`, `502`, `503`, `504` с учётом `Retry-After`. Переходы по HTTP-редиректам запрещены. При HTTP-ошибке или достижении лимита в 10 000 страниц скрипт завершится с ошибкой, не возвращая частичный отчёт.

## Запуск

Нужны Python 3.10+ и действующий токен amoCRM с доступом ко всем проверяемым сделкам и задачам. Скрипт поддерживает аккаунты на домене `amocrm.ru`.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

В Windows PowerShell активация окружения: `.venv\Scripts\Activate.ps1`.

Передайте в окружение:

- `AMO_SUBDOMAIN`: только поддомен аккаунта, без `https://` и `.amocrm.ru`
- `AMO_ACCESS_TOKEN`: действующий токен доступа

Токен вводите через локальное окружение или менеджер секретов. Не записывайте его в код, README, историю команд или Git. Файлы `.env` игнорируются Git, но сам скрипт их не загружает.

```bash
python amocrm_overdue.py
```

Вывод JSON идёт в stdout. Названия сделок могут содержать данные клиентов, поэтому реальный отчёт нельзя публиковать вместе с кодом.

## Проверка и ограничения

```bash
python -m unittest discover -s tests -v
```

**18 офлайн-тестов пройдены** на Python 3.13.5, requests 2.32.3 и urllib3 2.3.0. Используются настоящие requests/urllib3 и подменённые HTTP-ответы; реальные токены и сетевые запросы тестам не нужны. Проверены пагинация обеих коллекций, объединение задач со сделками, фильтрация, граничный срок, пустые ответы, ошибки авторизации/транспорта/JSON, запрет редиректов и лимит страниц. Политика повторов, `Retry-After`, backoff и исчерпание попыток проверены отдельно на объектах urllib3.

**В реальную CRM запросы не выполнялись.** Это не интеграционный тест API и не проверка на реальных данных. Повторы HTTP-запросов через реальное сетевое соединение не проверялись. CI в репозитории не настроен.

Ограничения компактного примера:

- Срез не атомарный: данные могут измениться между запросами, а `now` фиксируется после загрузки сделок
- Задачи контактов и компаний не учитываются
- Полнота зависит от прав токена; отсутствие видимой задачи не доказывает отсутствие скрытой задачи
- Обновление OAuth-токена, постоянное хранение состояния и строгая проверка всей схемы API не реализованы
- Пустой объект или отсутствующий блок коллекции трактуется как пустая выборка; для production нужна строгая валидация ответов и проверка полноты
- Пауза между запросами ограничивает частоту одного запуска; общий лимит нескольких параллельных процессов не координируется
- Это текущий срез, без исторического аудита за 30 дней, телефонии, ASR и LLM
